# Warranty Module Analysis

## 1. Class hierarchy and duration without duplication
Both warranty types share common attributes (id, product, sale, start date, end date) but differ in duration, coverage and cost. This is modeled with an abstract class Warranty that holds the shared attributes and common behavior (isActive, generateWarrantyCertificate), and two concrete subclasses, BasicWarranty and ExtendedWarranty, that override three abstract methods: getDurationInMonths(), getWarrantyType() and getAdditionalCost(). The OOP mechanism is method overriding (runtime polymorphism): the parent constructor calls the abstract duration method, and Java dispatches it to whichever subclass is actually being built, so each subclass supplies its own duration without any if/else and without duplicating the shared fields or the certificate-printing logic.

## 2. Where the console-only rule lives
This decision belongs to the service layer, specifically inside SaleService.registerSale, because it is a business rule about when a sale should trigger a warranty, not something the product entity or the persistence layer should know about. The mechanism used to verify the real type of a product is Java's instanceof pattern matching: if (product instanceof Console). This avoids adding an artificial flag such as isConsole() to Product and keeps the type check where the business rule is applied.

## 3. Where and how the expiration date is calculated
The expiration date is calculated once, inside the Warranty constructor, by calling the (overridden) getDurationInMonths() and adding it to the start date with startDate.plusMonths(...). Doing it in the constructor, instead of a separate method the caller must remember to invoke, guarantees that a Warranty object can never exist in an inconsistent state with a missing or wrong end date — it is always valid immediately after construction. The only caveat is the classic warning about calling an overridable method from a constructor; it is safe here because both overrides return a fixed literal (6 or 12) that does not depend on any field of the subclass being initialized.

## 4. Where the extended-warranty cost is applied
The extra cost is produced by ExtendedWarranty.getAdditionalCost() (10% of the product price) and applied inside SaleService.registerSale, right after the Sale object is created: the method calls sale.addExtraCost(extendedWarranty.getAdditionalCost()). registerSale needs three additive changes: (1) a new parameter, List<String> productIdsWithExtendedWarranty, empty/null meaning no extended warranty is requested; (2) a loop over the sold products that calls WarrantyService.assignBasicWarranty for every Console and, when requested, assignExtendedWarranty; and (3) the call to sale.addExtraCost(...), which Sale.calculateTotal() now includes in the sale total.

## 5. Where "expiring soon" lives
This query lives in WarrantyService (service layer). It needs the full in-memory collection of warranties (loaded once from the repository) and LocalDate.now() to compare against — both are business-logic concerns, not file-reading concerns (persistence) and not console I/O concerns (ui). Its only dependency is the List<Warranty> the service already keeps in memory. This is coherent with the layered architecture (ui → service → persistence → model): the service layer is the only one allowed to hold and iterate collections of domain objects to answer a business question; the persistence layer only knows how to read/write lines of text, and the ui layer only knows how to ask for input and print results.
